# Changelog

All notable changes to this project are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[semantic versioning](https://semver.org/spec/v2.0.0.html).

## [0.2.0] - 2026-08-25

The tracker becomes an application. Everything the repository did before still
works; there is now a domain model, a workflow engine, two interfaces, and a
migration between the two data formats.

### Added

**Domain model.** A typed `Paper` with a research question, repository and
manuscript path, target venue, authors, tags, research programme, a full set of
lifecycle timestamps, external identifiers, observed activity, submission
history, and transition history. Frozen dataclasses, timezone-aware datetimes,
validation at every boundary.

**Sixteen lifecycle states** from `idea` to `published`, plus `paused` and
`abandoned`, with a canonical transition graph. Non-canonical moves are refused
unless explicitly forced, and a forced move is recorded as forced.

**One next action per paper**, as a value object with an optional deadline. An
active paper without one is detected as a workflow problem; a paper waiting on a
venue or a co-author is exempt.

**Stage-dependent staleness.** `stale ⟺ (now − last activity) > d_stage`, with
`d_draft = 14` and `d_under_review = 180` by default, all configurable.

**Reminder engine** producing structured `Reminder` objects — kind, severity,
message, deadline, context — across three families: deadlines, inactivity, and
workflow problems.

**Manuscript stagnation detection.** When the repository or its analysis moved
within 7 days but the manuscript has not moved in 30, the paper is reported as
analysis-active and manuscript-stalled. Both thresholds are configurable.

**Path-based activity classification.** Manuscript, analysis, and data activity
are read separately from GitHub using path filters, so "when did the manuscript
last change" is a fact rather than an inference from commit messages. A paper's
own `paper_path` takes priority over the configured defaults.

**Append-only event log** (`data/events.jsonl`): creation, status changes, next
actions, deadlines, detected activity, submissions, decisions, issue syncs, and
migrations. The primary model stays state-based; events are history.

**Research pipeline analytics**: median idea→draft, draft→submission,
submission→decision, revision→resubmission, acceptance→publication, and
idea→publication, each with its sample size, plus portfolio counts and an
acceptance rate. Intervals with insufficient history report unavailable rather
than a fabricated number.

**Web application** (FastAPI, server-rendered Jinja2, no build step): portfolio
dashboard, paper list, paper detail, lifecycle Kanban, deadline calendar,
analytics, and settings, plus a JSON API at `/api/*`. Started with
`article-reminders serve`.

**Command line** (`article-reminders`): `list`, `show`, `add`, `update`,
`status`, `next-action`, `reminders`, `dashboard`, `board`, `calendar`,
`analytics`, `submit`, `decision`, `events`, `sync-github`, `migrate`,
`legacy-export`, `validate`, `settings`, `serve`. The CLI and the web application
share one service layer.

**Configuration** through an optional `article-reminders.yml`: storage paths,
per-stage staleness, reminder thresholds, stagnation thresholds, activity paths,
and GitHub settings. Every value has a working default;
`article-reminders.example.yml` documents all of them.

**Example portfolio** under `examples/`, regenerated deterministically by
`python examples/build_seed.py`, covering a stalled manuscript, a revision with a
deadline, a paper under review, an idea with no next action, and a published
paper with a DOI.

**Packaging and tooling**: `pyproject.toml` (Poetry), `ruff`, `mypy --strict`
over `src`, `pytest`, and `pre-commit`.

**Tests**: 345 covering the domain, the rules, the services, the reminder engine,
activity classification and stagnation, the GitHub client, activity gateway and
issue synchronisation (all mocked), analytics, the migration, the CLI, and the
web application.

### Changed

- `data/portfolio.json` is now the source of truth. `data/articles.json` remains
  readable, is read directly when no portfolio exists, and is regenerated by
  `article-reminders legacy-export`.
- `.github/workflows/article-reminders.yml` now runs the application rather than
  `scripts/sync_article_issues.py`: it migrates, refreshes activity, exports the
  legacy tracker, synchronises issues, and commits the refreshed data. The issue
  conventions are unchanged, so existing issues are reused rather than
  duplicated. **Do not schedule both issue synchronisers.**
- `.github/workflows/validate.yml` now runs `ruff`, `mypy`, both validators, the
  example-portfolio build check, and `pytest`.
- Reminder issue bodies now lead with the stage and the next action, list the
  paper's current reminders, and carry a hidden id marker for reliable matching.

### Preserved

- `scripts/validate_articles.py`, `scripts/sync_article_issues.py`,
  `scripts/sync_project_items.py`, and `scripts/check_article_drift.py` are
  unchanged, along with their tests. They still run.
- `project-sync.yml` and `drift-check.yml` are unchanged and keep reading
  `data/articles.json`.
- All 65 legacy entries round-trip through the new model byte for byte, and the
  test suite asserts it against the real data file.
- The orphan-issue safety rule — never close reminders when the portfolio is
  empty — is reproduced in the new synchroniser and tested.

### Migration

```bash
article-reminders migrate --dry-run   # report what would happen
article-reminders migrate             # write data/portfolio.json
```

The legacy file is never modified. An existing portfolio is backed up to
`data/backups/` before it is touched. Unknown keys are preserved and reported.
Running it twice does nothing the second time. Ids are derived from the entry's
identity, so they are stable across loads and across the migration itself.
